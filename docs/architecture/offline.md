# Offline Support & PWA

Turboist runs as an offline-capable PWA. The frontend treats IndexedDB (via Dexie) as the source of truth; the REST API and Server-Sent Events (SSE) drive background synchronization. Mutations made while offline are queued in an outbox and replayed when the network returns.

This document covers both halves of the contract:

1. Backend sync API (`/api/v1/sync/pull`, `clientId`, `deleted_at`, idempotency, Last-Write-Wins).
2. Frontend layout: Dexie schema, outbox, sync runner, PWA shell, offline auth.

## Backend sync contract

### Soft delete and `client_id`

Every synchronized entity (`tasks`, `projects`, `sections`, `labels`, `contexts`) has two extra columns:

- `client_id TEXT NULL UNIQUE` — ULID generated by the client before the server has assigned a numeric `id`. Used for idempotent inserts and for remapping references in the outbox.
- `deleted_at TIMESTAMP NULL` — tombstone. List queries filter `deleted_at IS NULL` by default; `/sync/pull` includes tombstones so clients can remove them locally.

`DELETE` requests perform a soft delete (`deleted_at = now()`). Any subsequent `PATCH` / `DELETE` against a tombstoned row returns **`410 Gone`** — tombstones are final.

Every write touches `updated_at = now()` unconditionally so monotonic ordering holds across the cluster of clients.

### `Idempotency-Key` middleware

All mutating endpoints (`POST`, `PATCH`, `DELETE`) accept an `Idempotency-Key: <ulid>` header. The server stores `(user_id, key) → (status, response_body)` in `idempotency_keys` for 24 hours; a repeat of the same key returns the cached response byte-for-byte. Different keys are always independent. Expired entries are evicted lazily on lookup.

The header is required for `POST` (so clients can safely retry creates) and recommended for `PATCH` / `DELETE`.

### Last-Write-Wins on `PATCH`

`PATCH` may include either:

- `baseUpdatedAt` in the JSON body, **or**
- `If-Unmodified-Since` header.

If the server's `updated_at` is newer than the supplied value, the patch is silently ignored and the server returns its current canonical entity (no `409`). This keeps the protocol simple — conflicts resolve via wall-clock ordering. Whole-record LWW only; field-level merge is not attempted.

### `POST /api/v1/sync/pull`

Returns every change the caller hasn't seen yet, across all synchronized domains, in one round-trip.

Query: `?since=<RFC3339>` (optional).

- With `since` — returns rows where `updated_at > since`, including tombstones.
- Without `since` (initial pull) — returns open tasks plus completed tasks from the last 30 days, and all rows from the other domains.

Response:

```json
{
  "now": "2026-05-25T12:00:00.000Z",
  "tasks":    [{"id": 42, "clientId": "01J...", "deletedAt": null, ...}],
  "projects": [...],
  "sections": [...],
  "labels":   [...],
  "contexts": [...]
}
```

Clients persist `now` as `meta.lastPulledAt` and use it as `since` on the next call.

### Mutation request shape

`POST` / `PATCH` accept an optional `clientId` field in the body. The server stores it on first write and echoes it back in the canonical response so the client can remap any pending outbox references from `clientId` → server `id`.

## Frontend offline layer

### Directory layout

```
frontend/src/lib/offline/
  db.ts                  Dexie schema + version migrations
  ids.ts                 newClientId() (ulid) + ref helpers
  outbox.ts              pending mutations queue + retry state machine
  sync.ts                pull/push runner
  stores.ts              bridge: Dexie ↔ Svelte stores via custom events
  cache.ts               read/write helpers per entity table
  auth.ts                Dexie-backed auth adapter (offline login persistence)
  taskMutations.ts       optimistic create/update/delete/complete/move for tasks
  entityMutations.ts     same pattern for projects/sections/labels/contexts
  tasksStore.svelte.ts   Dexie-backed tasks store factory
  entityStore.svelte.ts  generic Dexie-backed store factory
  outboxStatus.svelte.ts UI-facing pending/failed counts
```

### Dexie schema

Tables: `tasks`, `projects`, `sections`, `labels`, `contexts`, `meta`, `outbox`.

- Entity tables use `clientId: string` as the primary key. The server `id: number` is a secondary index, used for lookup after the first successful create.
- `meta` holds one row with `{ lastPulledAt, userId }`.
- `outbox` is keyed by ULID and stores:

```ts
{
  id: string,                       // ulid
  entity: 'task' | 'project' | ...,
  op: 'create' | 'update' | 'delete' | 'action',
  payload: unknown,                 // body sent to the API
  baseUpdatedAt?: string,           // for LWW
  enqueuedAt: number,
  attempts: number,
  nextRetryAt: number,
  status: 'pending' | 'inflight' | 'failed',
}
```

### Mutation lifecycle

```
user action
  → store.optimisticApply()          // Svelte $state updates, UI is instant
  → db.put(entity)                   // IndexedDB becomes the source of truth
  → outbox.enqueue(op)               // record intent
  → if online: sync.flush()
        ApiClient.fetch(...) with Idempotency-Key
        OK            → outbox.remove(); db.put(server-canonical); remap refs
        net error     → exponential backoff (1s, 2s, 5s, 15s, 30s, 60s)
        4xx           → status = 'failed'; toast with Retry / Discard
        410 (gone)    → drop from outbox; remove tombstoned row from Dexie
```

`sync.flush()` topologically sorts the outbox so parents are sent before children — a child task created offline against a still-unconfirmed parent stays queued behind the parent's `POST`, and its `parentId: { kind: 'ref', clientId }` reference is rewritten to the server id once available.

### Read path

On layout boot the store hydrates synchronously from Dexie (UI renders immediately, no network needed) and starts `sync.pull(meta.lastPulledAt)` in parallel. Each Dexie write fires a `turboist:db-changed:<entity>` event; stores re-hydrate the affected slice. SSE events trigger a scoped `sync.pull` rather than reloading directly from REST, so all writes funnel through Dexie.

### Offline auth

- Access tokens (15 min) and refresh cookies (HttpOnly) are useless without the network.
- On boot, if Dexie has data and `meta.userId` matches the last logged-in user, the UI is granted entry — even if `/auth/refresh` fails with a network error.
- The first successful refresh triggers `sync.flush()` so queued mutations replay.
- On explicit logout, or on a `401` from `/auth/refresh` while online, Dexie is wiped (`db.delete()`) to prevent cross-user data leaks.

### PWA shell

`@vite-pwa/sveltekit` generates the service worker. Strategy:

- **CacheFirst** for build assets (JS, CSS, icons, locale JSON) — precached at install.
- **`/api/*` is never cached by the SW.** Data lives in IndexedDB; double-caching would split the source of truth.
- **Navigation fallback**: the cached `index.html` is served when offline so SvelteKit can pick up the route on its own.

`manifest.webmanifest` and icons are wired for "Add to Home Screen" on Safari and Chrome.

### UX surface

- `OfflineIndicator.svelte` — network status pill in the topbar.
- `PendingSyncBadge.svelte` — counter sourced from `outboxStatus.svelte.ts` showing how many mutations are waiting.
- `FailedSyncToasts.svelte` — surfaces failed outbox entries with Retry / Discard actions.

## Conflict-resolution edge cases

- **delete vs edit**: tombstones are final. An edit arriving after a delete is rejected with `410 Gone` rather than resurrecting the row.
- **complete vs edit**: whole-record LWW — the patch with the later timestamp wins; minor field loss is accepted as the cost of simplicity (acceptable for a single-user multi-device app).
- **Search**: offline search runs as a plain JS filter over the Dexie cache (`title`, `notes`). The server-side `/api/v1/search` endpoint is still used when online for richer results.
- **SSE while offline**: silently dropped. On reconnect the client issues `sync.pull(since=lastPulledAt)` and the EventSource is re-established.
